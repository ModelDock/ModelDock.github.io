Architecture & System Design

A deep architectural breakdown of ModelDock's asynchronous micro-backend, standalone llama.cpp process supervisor, and native Windows WebView2 container.

System Architecture

ModelDock is partitioned into decoupled layers to maintain responsiveness, low resource utilization, and crash isolation:

Core Subsystems

Module File Responsibility Key Implementation Detail
run.py FastAPI Core App & Routes Non-blocking ASGI event loop, CORS middleware, and OpenAI /v1 proxy routes.
desktop_app.py Edge WebView2 Shell Spawns the local webview with native window handles, custom icon, and graceful shutdown signal handlers.
core/engine_manager.py Process Controller Manages the lifecycle of bin/llama-server.exe, monitors port health, and frees VRAM on unload.
core/downloader.py Chunked Downloader Performs byte-range requests with pause/resume support, SHA256 integrity verification, and layered chunks.
core/hf_hub.py Hugging Face Hub Client Direct queries to HF API, file tree parsing, and token authentication for gated model access.
core/gguf_parser.py Binary GGUF Header Parser Reads binary tensor metadata, quantization format, and context length directly without loading full weights into RAM.
core/system_monitor.py System Telemetry Zero-overhead memory, CPU percentage, and NVIDIA NVML GPU VRAM telemetry reporting.

Process Lifecycle & Memory Safety

To prevent memory leaks and zombie processes:

  • Crash Isolation: The heavy C++ inference engine runs as an independent OS subprocess (llama-server.exe). If a model triggers an out-of-memory (OOM) error, the Python server and UI remain fully operational.
  • Graceful Teardown: When the desktop window or browser server is terminated, a Windows SIGTERM/SIGINT handler terminates any active engine subprocesses before exiting.
  • VRAM Purging: Switching models triggers an explicit shutdown of the active engine instance, resetting CUDA memory allocators before the new model is loaded into VRAM.
